# 성능 실측 보고서 (Sprint 5, Performance Engineer)

2026-10-02. 측정과 보고만 했고 `cmd/`, `internal/` 제품 코드는 바꾸지 않았다. 목표치는 제안이며 PRD 7장은 PO가 정한다. 모든 수치는 실제 실행 결과이고 추정은 "(추정)"으로 표시했다.

## 1. 머신과 방법

| 항목 | 값 |
| --- | --- |
| CPU / RAM | i5-10400 6C/12T (800 MHz~4.3 GHz, governor `powersave`), 7.6 GiB, 측정 중 다른 부하 없음 |
| 디스크 | NVMe `nvme0n1p5`, ext4, ROTA=0. **fsync 약 5 ms** (`dd bs=4k oflag=dsync` 823 kB/s) |
| 소프트웨어 | Linux 7.0.0-34, Go 1.27.1 linux/amd64, `go build` 기본값, modernc.org/sqlite v1.60.1 (SQLite 3.53.4). 비교용 mattn/go-sqlite3 v1.14.52 (cgo, gcc) |
| 설정 | `ulimit -n` 1,048,576, 12 worker(NumCPU), pool 64/worker, batch 500 / 50 ms, WAL + `synchronous=NORMAL` |
| 재현 | `go test -tags perf -run TestPerf ./internal/{ingest,query,stream}`, `scripts/bench.sh`, `tclient bench-feed/-http/-ws/-sink` |

- 변형(batch, flush, pool, worker 수, sync, cache_size, 드라이버, 인덱스, 쿼리 힌트)은 저장소 밖 복사본에서 env 노브로 바꿨다. 저장소에는 `*_bench_test.go`(`//go:build perf`), `scripts/bench.sh`, `cmd/tclient/bench.go`만 추가했다.
- 조건당 3회 이상 반복, 중앙값(최소-최대). 반복이 모자란 칸은 n을 적었다. 클라이언트가 같은 머신 CPU를 쓰고 loopback이다. powersave 때문에 일부 칸은 회차 편차가 최대 2배다.
- 틱 분포: mockfeed는 종목 균등 무작위, ts는 틱당 평균 +100 ms(1M틱 = 27.7시간, 자정을 넘어 일자 2개). bench-feed는 종목 라운드로빈, ts=현재, qty=1.
- 결과를 **cold start**(일자 파일 신규 생성 포함)와 **steady**(파일 이미 있음)로 나눴다. 종목이 많을수록 차이가 크다.

- worker는 5종목에서 6개로 포화, 100종목은 12까지 증가(6코어/12스레드).
- **pool 절벽**: 활성 파일이 worker x pool(768)을 넘으면 매 커밋이 close(체크포인트+fsync)+reopen이 되어 5~20배 느려진다. 500종목은 worker당 42개라 안전, 2000종목(worker당 167개)은 걸린다.
- **파일 생성 속도**(모든 틱이 새 일자 파일, 100종목 600틱, 3회): 현재 **47-48 files/s**(파일당 약 80 ms). `strace`로 파일당 fsync 24회 확인. `store.build`가 `schema.sql` 4문장을 autocommit으로 실행하고 `synchronous` 기본값(FULL)이라 문장마다 journal fsync가 난다. 스크래치 변형: 스키마를 한 트랜잭션으로 93 files/s, 빌드 중 `synchronous=OFF` 141 files/s. 3000종목 파일 생성에 약 60 s(현재) / 21 s(변형) (추정, files/s 기준).

## 5. [측정 4, 5] 조회 지연

### 5.1 n-tick 단일 클라이언트 (인프로세스 20회; QA = 30일 x 200k, QB = 10일 x 1M)

| (n, m) | 읽은 행 | warm p50 (p95) | REST p50 (p95) | cold p50 | CPU/호출 |
| --- | --- | --- | --- | --- | --- |
| (100, 200) | 20k | 18.3 ms (18.9) | 20 ms (20.7) | 34 ms | 18 ms |
| (1000, 200) | 200k | 177 ms (180) | 191 ms (193) | 324 ms | 178 ms |
| (1000, 1000) | 1M | 886 ms (894) | 953 ms (1002) | 1.63 s | 893 ms |
| (10000, 100) | 1M | 887 ms (894) | 949 ms (953) | 1.63 s | 894 ms |
| (10000, 1000) QA | 6M (캔들 600) | 5.31 s | 5.72 s | 9.78 s | 5.36 s |
| (10000, 1000) QB | **10M** | **8.93 s** | **9.62 s** | **16.4 s** | 9.0 s |

- 행당 약 890 ns(warm) / 1.64 us(cold), 데이터 크기와 무관하게 선형. 읽은 행 = min(m*n, 보유 틱)로 PRD 상한 준수. REST 오버헤드 약 8%(응답 12-124 KB). 서버 RSS 24 MB, 5xx 없음.
- cold는 호출 전 `posix_fadvise(DONTNEED)`로 해당 파일 page cache를 비워 측정(root 불필요). 전체 drop_caches는 쓰지 않았다.
- 비용 분해(QB 1M행, modernc): 현재 계획(partial index + rowid 조회) 833 ms, 엔진만 580 ms. **인덱스 없이 테이블 역스캔(`NOT INDEXED`) 411 ms**, 커버링 인덱스 415 ms, SQL 윈도 집계는 2.2 s(더 느림). 실제 코드 경로에 `NOT INDEXED` 힌트를 넣은 변형은 (1000,1000) 492 ms, (10000,1000) 4.9 s로 1.8x. `ix_ticks_valid`를 뺀 스키마도 490 ns/행으로 같다.
- **m*n 상한 (warm, 단일, p95)**: 100 ms **약 105k**, 500 ms **약 550k**, 2 s **약 2.2M** (측정: 100k=94 ms, 120k=110 ms, 500k=452 ms, 600k=583 ms, 2M=1.82 s, 2.5M=2.25 s). cold는 x0.55, `NOT INDEXED`/인덱스 제거는 x1.8, mattn은 x1.36.

## 8. [측정 8] 파일 디스크립터

공식: `열린 파일 x 3`(db, -wal, -shm) + 기본 약 7-40. 열린 파일 = min(활성 파일 수, worker x pool), pool = clamp(soft/2/(3 x worker), 4, 64).

| 시험 | 예측 | 실측 최대 (`/proc/PID/fd`) |
| --- | --- | --- |
| 500종목, `ulimit -n` 1M (pool 64) | 500x3+7 = 1,507 | 1,507 |
| 500종목, `ulimit -n` 1024 (pool 14) | 12x14x3 = 504 + 기본 | 542 |
| 2000종목, 1M (pool 64) | 12x64x3 = 2,304 + 기본 | 2,343 |
| 2000종목, `ulimit -n` 4096 (pool 56) | 12x56x3 = 2,016 + 기본 | 2,056 |
| 2000종목, pool 256 (스크래치) | 2000x3 = 6,000 + 기본 | 6,007 |

공식이 맞는다. 메모리는 별개로 **열린 파일당 RSS가 기본 cache_size(약 2 MB) 때문에 최대 약 4 MB**다(100종목 steady RSS 418 MB). 스크래치 `PRAGMA cache_size=-256`에서 100종목 RSS 87 MB, 처리량 동일(264k-292k). pool 64 x 12 = 768파일이 차면 약 3.2 GB(추정).

## 9. 병목 순위 (영향 큰 순)

1. **LRU pool 절벽**: 활성 파일 > 768이면 커밋마다 close+reopen. 2000종목 steady 1.1k tick/s (pool 256이면 26k, 23배). 수천 종목이 섞이는 실제 시세에서는 반드시 걸린다.
2. **n-tick 조회 비용**: 890 ns/행 x 최대 10M행 = 9 s(warm), 16 s(cold). PRD 상한(m*n=10M)이 어떤 지연 목표와도 맞지 않는다. 인덱스 경유 행 조회가 절반.
3. **modernc 읽기 동시성 불가**: 동시 조회 2개부터 처리량이 늘지 않고 CPU만 소모, 수집을 최대 -63% 깎음. (1000,200)이 유휴 0.19 s -> 8 클라이언트 1.06 s -> 수집 병행 2.0 s.
4. **신규 일자 파일 생성 48 files/s**(파일당 fsync 24회): 장 시작 시 3000종목에 약 60 s.
5. **커밋 입도**: 종목이 많으면 틱 1-3개/커밋(batch 100->2000에서 +78~87%, 500종목 steady 79k vs 5종목 478k).
6. `synchronous=FULL`은 -57~-67%.
7. `ix_ticks_valid`: 저장 37%, 1종목 수집 -32%(233k vs 340k), 조회 1.8x 느림. valid=1 필터 외 용도 없음.
8. 열린 파일당 메모리 최대 4 MB(기본 cache_size).
9. 구독 1000개 = 1코어 이상. 느린 구독자 감지가 소켓 버퍼에 의존하고 close 사유가 전달되지 않음.
10. 장기 reader가 WAL을 키움(116 B/틱). 10M행 조회(9 s)가 이에 해당.

### (b) 캐시(PRD 5.4)가 지금 필요한가
- 옵션 A: 캐시 없이 m*n <= 500k + 인덱스 제거. 옵션 B: 과거 일자 (symbol, date, n) 캐시(불변이라 적중 시 DB 미접근).
- **선택: 지금은 도입하지 않는다.** A로 대부분 질의가 500 ms 안이다. m*n > 500k를 허용해야 하면 B가 필요하다(10M행은 캐시 미스 시 9 s).

### (c) SQLite 드라이버
- **선택**: 동시 조회 요구가 8 이상이면 mattn(조회 5x 확장, 1종목 수집 +38%, 바이너리 -15%). 단 다종목 수집 CPU 2배, cgo 빌드. 요구가 낮으면 modernc 유지 + 질의 동시 2 제한. 드라이버 교체 전에 (d)(e)의 저비용 수정이 먼저다(효과가 더 큼).

### (d) 배치 상수와 pool
- maxBatch 500 -> **2000**(+11~15%, 시간 flush가 먼저라 지연 무영향). flushInterval 50 -> **20 ms**(실시간 목표에 따름, 10 ms도 CPU +2% 수준). queueSize는 미측정.
- **pool을 활성 종목/worker 이상(256+)으로 올리고 `cache_size`를 -256 정도로 줄여 메모리 상쇄.** 3000종목이면 fd 9,000(`ulimit -n` 상향). 근본 해법은 종목별 버퍼링(코드 변경).
- `store.build` 스키마를 단일 트랜잭션으로(93 files/s, 약 2배). `synchronous=NORMAL` 유지.

### (e) 조회에 day_index 사용
- **불필요.** 파일 고정 비용은 약 0.3 ms/파일(30파일 8.5 ms), `listDays`는 일자 디렉터리 250개에서 0.8 ms(31개 0.4 ms). 병목은 행 스캔이다.

### (f) 보관·용량
- 현재 스키마 3000종목 x 250일 약 1.4 TB(추정), 인덱스 제거 시 약 0.87 TB(추정). 일자 디렉터리 삭제로 충분. 파일 750k개는 ext4에서 무리 없어 보이나(미시험) 파일 생성 48/s가 장 시작 병목. 보관 기간은 PO 입력 필요.
- `ix_ticks_valid` 제거(저장 -37%, 1종목 수집 +48%, 조회 1.8x)는 이득이 크지만 스키마·재판정 영향이 있어 PO 결정 항목이다. 대안은 쿼리에 `NOT INDEXED` 힌트(조회만 1.8x).

## 11. 측정하지 못한 것과 한계
- 전체 `drop_caches`(root 필요)는 못 써서 파일 단위 `fadvise DONTNEED`로 cold를 대체했다.
- 2000종목 e2e 1M틱은 회당 12-13분이라 혼합은 1회뿐이다(steady·인프로세스는 3회 이상).
- 1000 구독 지연은 같은 머신 클라이언트 CPU가 섞였다. 최대 속도 구성의 WS 지연은 대기열 지연이 지배해 비교하지 않았다.
- 실제 시세 분포(종목 편중, 장 시작 폭주)는 모른다. mockfeed 균등 분포 기준이다. `GOMAXPROCS`는 따로 바꾸지 않고 worker 수로 대신했다.
- 100k/s p99 꼬리의 원인(체크포인트 추정)과 750k 파일 규모의 ext4 동작은 확인하지 않았다.
