# 저장 구조 3종 쓰기 성능 비교 (Sprint 6, Performance Engineer)

2026-10-03. 같은 머신(i5-10400 6C/12T, 7.6 GiB, NVMe ext4, fsync 약 5 ms, `docs/perf-report.md` 1절과 동일), 같은 입력, 같은 PRAGMA(WAL, `synchronous=NORMAL`, busy_timeout)와 같은 배치 트랜잭션(tick insert + `day_stats` upsert + `candle_1m` upsert, ts 기반 open/close, 하루치)으로 쟀다. 제품 코드는 바꾸지 않았다. 권고가 아니라 PO 판단용 측정이다. 추정은 "(추정)"으로 표시했다.

## 1. 요약 (PO용)

- **A 현재 구조**: 프로세스 1개, 종목별 DB 파일. **B**: 프로세스 1개, DB 파일 1개(종목 id 열). **C**: 종목마다 writer 프로세스 1개, 종목별 DB 파일.
- A는 "현재 상수"(pool 64, batch 500)와 "튜닝"(pool 제한 없음, cache_size -256, batch 2000, 스키마 1트랜잭션)을 모두 쟀다. 공정하게 A는 튜닝본이 기준이다.
- 활성 종목 100개까지는 C가 가장 빠르지만 CPU를 코어 8~10개분 쓰고 프로세스 수만큼 메모리가 든다. 500종목 이상에서는 이 머신에서 C를 돌릴 수 없다(메모리). B는 어느 종목 수에서도 A 튜닝본보다 느리다(단일 writer 한계).

## 2. 주요 구조적 발견

1. **커밋 입도가 A의 성패를 가른다.** A 현재는 종목이 늘수록 커밋당 틱이 줄어(5종목 482 -> 100종목 55 -> 500종목 12 -> 2000종목 3) 틱당 저장소 쓰기가 149 -> 540 -> 1,712 -> 24,165 B로 는다. 2000종목은 pool 절벽(845~1,479 tick/s)이다. 튜닝본은 같은 구성에서 47k.
2. **B는 단일 writer 상한이 낮고 쓰기 증폭이 크다.** 한 트랜잭션에 여러 종목이 섞이면 종목마다 인덱스 leaf, `day_stats`, `candle_1m` 페이지를 건드려 WAL 쓰기가 틱당 2.8 KB(100종목 batch 500), 15.7 KB(500종목)다(A 튜닝 242 B, 629 B). batch를 5000으로 키우면 572 B/2.4 KB로 줄고 처리량이 1.4~3.7배 늘지만 커밋 지연 p50이 17~100 ms가 된다. CPU는 한 코어의 60~90%만 쓴다.
3. **B의 cross-symbol 정지.** B는 모든 종목이 한 커밋 줄에 선다. 커밋 지연 p99가 p50의 2~6배(100종목 batch 500: 3.4 -> 20.8 ms, 2000종목 batch 2000: 70 -> 194 ms)이고, 이 꼬리 동안 전 종목이 같이 멈춘다. 체크포인트 때문이라는 것은 정황 추정이며 직접 분리해 재지는 않았다. A는 한 파일의 정지가 그 worker의 종목(약 1/12)에만 영향을 준다.
4. **C의 비용은 프로세스 수에 비례한다.** 프로세스당 RSS 16~18 MB(`rss_per_child`), fd 약 13개(C-b는 파이프 포함 약 16개), 스레드 약 9~10개. 300개에서 RSS 4.85 GB로 `MemAvailable` 하한(1.2 GiB)에 근접해 더 가지 않았다. 500/2000/3000 외삽은 6절(추정).
5. **C-b의 라우터는 병목이 아니고, 병목은 분할 배치다.** 라우터 단독 한계는 100프로세스에서 8.1M, 200에서 5.9M msg/s(CPU 약 1.9코어)지만 실제 C-b에서 라우터 CPU는 24~43%다. 그런데도 C-b가 C-a보다 느린 이유는 틱이 프로세스별로 잘게 나뉘어 커밋 크기가 줄기 때문이다(200프로세스 커밋당 227틱 vs 352, 300프로세스 102틱, 처리량 251k vs 615k).
6. **A 튜닝본의 효과는 종목이 많을수록 크다.** 5종목 1.15배, 100종목 1.9배, 500종목 1.4배, 2000종목 30배(cold 38배). 그래서 C와의 비교는 A 튜닝본 기준으로 읽어야 한다.
7. **cold start**: B는 파일이 하나라 생성 비용이 없다(2000종목 batch 5000 cold 41k / steady 40k). A 현재는 2000종목 cold 845 tick/s(파일 생성 약 48 files/s가 겹침), A 튜닝은 32k.

## 3. 방법

- 하네스: `cmd/tclient/bench_modes.go`(`tclient modes-run | modes-read`, 내부용 `modes-child`)와 `scripts/bench_modes.sh`, 집계 `scripts/bench_modes_sum.py`. 제품 코드는 그대로 두었고 per-batch 트랜잭션 SQL은 제품(`internal/ingest/worker.go`, `store/candle.go`) 것을 복제했다. 데이터와 로그는 scratchpad에만 썼다.
- **A-prod**는 실제 `ingest.New`(제품 코드), **A-cur**는 같은 동작을 하는 하네스 구현이다. 두 값이 5/100/500종목에서 +-6% 안에서 같아(예: 100종목 steady 235k vs 248k) 하네스 값을 신뢰한다. A-tuned만 하네스 구현을 쓴다.
- 입력: 균등 = 종목 라운드로빈, 치우침 = Zipf(s=1) 고정 시드. 6시간에 걸친 ts, 하루치, 전부 valid. 틱은 미리 생성해 메모리에 둔다.
- B 스키마: `ticks(raw_seq PK, symbol_id, ts, price, qty, valid)`, `ix_ticks_sym(symbol_id, raw_seq) WHERE valid=1`, `day_stats(symbol_id PK)`, `candle_1m(symbol_id, minute) WITHOUT ROWID`. writer 1개가 연결 1개와 준비된 구문을 재사용한다(A보다 유리한 조건).
- C-a: 프로세스마다 자기 입력을 생성(배분 비용 없음). C-b: 라우터(부모)가 38바이트 wire 메시지를 디코드해 종목 소유 프로세스에 파이프로 전달(4 KB 단위, 2 ms마다 flush).
- 처리량 = 입력 완료부터 모든 DB 닫힘(drain)까지. steady = 종목당 1틱 선생성 패스 후 측정. CPU/RSS/fd는 부모와 자식 합계(RSS는 입력 배열 제외한 순증가). 3회 중앙값(최소-최대).
- 안전: 실행 전 `MemAvailable` 1.4 GiB 미만이면 건너뛰고, 실행 중 1.2 GiB 미만이면 중단하도록 했다. 이번 측정에서는 한 번도 발동하지 않았다. 종료 시 자식 프로세스 kill trap.

| --- | --- | --- | --- | --- |

## 8. 어느 모드가 언제 이기나 (측정 범위 안에서)

| 상황 | 가장 빠른 모드 | 비고 |
| --- | --- | --- |
| 활성 종목 <= 10 | C-a 1.26M > A 튜닝 680k > B 240k | A로도 충분하면 구조 변경 이득이 작다 |
| 활성 종목 100 | C-a 993k, C-b 715k > A 튜닝 476k > B 142k | C는 CPU 8코어, RSS 1.8 GB |
| 활성 종목 200~300 | C-b 478k(200) / 251k(300) | A 튜닝은 미측정(100에서 476k, 500에서 146k 사이) |
| 활성 종목 500 | A 튜닝 146k > B 74k | C는 이 머신에서 불가 |
| 활성 종목 2000 | A 튜닝 47k > B 40k | A 현재 설정은 1.5k로 사실상 불가 |
| 종목 수와 무관한 메모리·fd | B (42 MB, fd 10) | 처리량은 batch 5000에서도 A 튜닝의 30~85% |
| 읽기(n-tick) | A = C | B는 2.1배 느림 |

- B는 "프로세스 하나, 파일 하나"의 단순함(fd 10, RSS 42 MB, cold start 비용 없음)을 주는 대신 처리량 상한이 낮고 쓰기 증폭이 크며 읽기도 느리다.
- C는 처리량 상한이 가장 높지만 프로세스당 고정 메모리 때문에 종목 수가 수백을 넘으면 비현실적이다. 운영 복잡도(프로세스 감시, 재시작, 종목 재배정)는 측정 범위 밖이다.
- A는 상수(pool, batch, cache_size, 스키마 트랜잭션)만으로 가장 큰 개선(2000종목 30배)을 얻는다.

## 9. 측정하지 못한 것과 한계

- C는 500종목 이상을 못 쟀다(메모리 한계, 300프로세스에서 RSS 약 5 GB). 외삽은 6절의 추정뿐이다.
- 예산 때문에 1M틱 미만인 칸: A 현재 2000종목(100k틱), A 튜닝 2000종목 보조 행(100k틱), B batch 500 2000종목(400k틱). A-prod는 2000종목을 쟀지 않았다. C 300프로세스는 1회.
- A 튜닝 200종목은 측정하지 않았다(C와 직접 비교 불가). B의 batch 500 / 2000 / 5000 외 값, fsync 횟수 직접 계수(대신 `/proc/self/io write_bytes`로 쓰기 증폭을 쟀다)는 하지 않았다.
- B의 cross-symbol 정지의 원인(체크포인트)은 p99/p50 비로 추정했고 단독 검증하지 않았다.
- 틱은 모두 valid, 하루치, 메모리에서 생성한 입력이다. 실시간 푸시, 장애 복구, 내구성(kill -9) 동작, 운영 복잡도는 비교하지 않았다. 클라이언트와 라우터가 같은 머신 CPU를 쓴다. 일부 칸(B 100종목 cold, A-tuned 2000종목 cold)은 회차 편차가 컸다(표에 최소-최대 기록).
