# 내구성·이중화 확장 설계 메모

설계 검토 Q&A를 정리한 문서다. 코드는 바꾸지 않았고 수치는 실측만 적었다. 확인하지 못한 것은 "(미확인)"으로 표시했다. 측정은 저장소 밖 복사본에서 `TestPerfIngest`(`PERF_MODE=ingest`)로 했다.

## 1. n-tick 조회의 핵심 (현행 설계)

- 일자·종목별 SQLite 파일(`data/{YYYYMMDD}/{symbol}.db`). 종목당 writer는 하나다.
- `ticks(raw_seq INTEGER PRIMARY KEY, ts, price, qty, valid)`. `raw_seq`는 호스트 로컬 도착 순서(rowid)다.
- valid 개수는 `day_stats.valid_count`로 별도 관리한다. `last_raw_seq`와 함께 틱 INSERT와 **같은 트랜잭션**에서 갱신하므로 크래시가 나도 어긋나지 않는다.
- 조회: 한 읽기 트랜잭션에서 `day_stats`를 읽고, `r = T mod n`(0이면 n), `L = r + (take-1)*n`을 계산해 `WHERE valid=1 AND raw_seq <= last_raw_seq ORDER BY raw_seq DESC LIMIT L`로 읽는다. 가장 최신 캔들만 미완성이다. 부족하면 이전 일자 파일로 넘어간다(최대 30개).
- 쓰기 시 틱은 개별 INSERT하고 COMMIT만 묶는다.

## 2. 요구사항과 한계

- 요구: 매 틱 무유실.
- 수신 측만으로는 보장할 수 없는 구간이 있다: 커널 TCP 버퍼, COMMIT 전 메모리, OS 크래시·정전 시 공유메모리(RAM).
- 피드는 **전문별 시퀀스가 없고 ms 단위 ts만 있으며(중복 가능), 재전송이 불가**하다. 따라서 ts나 내용으로 중복을 판정할 수 없다(같은 내용 틱이 정상 존재).

## 3. 성능 실측 (modernc/sqlite, i5-10400, NVMe fsync 약 2~5 ms)

| 조건 | tick/s | 비고 |
| --- | --- | --- |
| 1종목, 틱마다 COMMIT + NORMAL | 6.9k–7.2k | OS 크래시 시 최근 커밋 유실 가능 |
| 1종목, 틱마다 COMMIT + FULL | 477–497 | fsync 지배 |
| 1종목, 틱마다 COMMIT + OFF | 약 12k | 내구성 없음(참고) |
| 5종목, 배치 500 + FULL, group commit | 237k / 253k / 504k (3회) | |
| 5종목, 배치 500 + FULL, 타이머 | 228k / 230k / 507k (3회) | group commit과 차이 없음 |
| 5종목, 배치 500 + NORMAL | 874k~905k(group) / 537k~567k(타이머) | |

- 틱마다 COMMIT은 처리량이 낮다. 배치 + FULL이 균형점이다(기존 보고서: NORMAL 대비 -57%~-67%).
- FULL 3회차가 약 505k로 튀는 원인은 미확인이다(클럭이나 fsync 편차 추정).
- 이 부하는 배치가 항상 가득 차므로 group commit의 지연 개선은 입증되지 않았다. 저부하 커밋 지연(p50/p99)은 미측정이다.

## 4. 목표 구조: 공유메모리 링 → SQLite

현재 구조는 수신부가 공유메모리 링에 쓰고 기록부가 읽어 저널 파일에만 저장한다. 이를 SQLite로 바꾼다.

```
수신부 → 공유메모리 링 → 기록부 → SQLite (FULL, group commit)
                           ↑ COMMIT 이후에만 링 읽기 커서를 전진
```

- **group commit**: 링에서 쌓인 전문을 최대 500개까지 읽어 종목·일자별로 나누고 파일당 트랜잭션 하나로 커밋한다. `synchronous=FULL`.
- **커서**: 공유메모리 헤더의 `read_seq`를 **COMMIT 이후에만** 갱신한다. 기록부가 재시작하면 이 값에서 이어 읽는다. OS 재부팅 시 링이 사라지므로 파일 영속화는 이득이 없다.
- **멱등 키**: 수신부가 쓸 때마다 증가하는 **64비트 비순환 카운터**를 각 전문의 시퀀스로 쓴다. 링 슬롯 번호는 순환하므로 쓸 수 없다. 링 재생성에 대비해 헤더에 `epoch`를 둔다. 키는 `(epoch, seq)`다. 수신부(C)에 카운터가 없으면 추가한다.
- **멱등 재생**: `day_stats.last_src_seq`를 틱과 같은 트랜잭션으로 갱신하고, 재생 시 `seq <= last_src_seq`는 건너뛴다. 한 배치가 여러 파일에 걸쳐 일부만 커밋돼도 파일별로 처리된다.
- **링 덮어쓰기**: `write_seq - read_seq > 용량`이면 덮어쓰기가 발생한 것이다. 건너뛴 구간을 로그와 별도 테이블에 기록하고 경보한다. 복사한 뒤 `write_seq`를 다시 읽어 슬롯이 읽는 도중 덮어쓰이지 않았는지 검증한다(seqlock).
- **용량**: `피크 틱률 × (기록부 최대 정지 + 재시작 시간)` 이상으로 여유를 둔다. 피크 틱률은 미확인이다.
- **기록부 언어**: Go(ntick `ingest`)가 mmap으로 링을 읽는 구성을 추천한다. 스키마, 유효 판정, `candle_1m` 집계, 이벤트, 조회를 재사용한다. C 기록부에 SQLite를 붙이면 같은 로직을 C로 다시 구현해야 한다. 링 구조체 레이아웃은 C와 정확히 맞춰야 하며 원자성 처리는 링 헤더를 보고 검증해야 한다(미확인).
- **전환**: 저널과 SQLite를 병행 기록하며 틱 수와 `valid_count`를 비교한 뒤 저널을 끈다.

### 유실 구간

| 상황 | 결과 |
| --- | --- |
| 기록부 크래시·재시작 | 링이 용량 안에서 보존하므로 무유실 |
| 링 덮어쓰기 | 감지·기록(막지는 못함) |
| 수신부 크래시, 수신 전 구간 | 재전송 불가이므로 복구 불가 |
| OS 크래시·정전 | 링의 미커밋분 유실. 커밋된 데이터만 보장 |

## 5. 수신부 이중화 (호스트 장애 대비, 재전송 불가)

**shared-nothing active-active.** 호스트마다 수신부, 링, 기록부, SQLite를 따로 두고 두 호스트가 같은 피드를 동시에 구독한다.

- 한 호스트가 죽어도 다른 호스트가 같은 틱을 저장하므로 시스템 전체로는 유실이 없다. 두 호스트가 동시에 죽거나 피드 자체가 유실하면 복구할 수 없다.
- **호스트 간 공유 seq는 만들지 않는다.** 전문에 시퀀스가 없고 두 호스트가 받는 틱 집합이 다를 수 있기 때문이다.
- `(epoch, seq)`와 `raw_seq`는 호스트 로컬이다(링→SQLite 멱등 재생용, 도착 순서).
- 같은 호스트 안의 active-standby(프로세스 장애용)라면 카운터를 공유메모리 헤더에 두어 번호를 이어 가고, `flock`이나 헤더 CAS로 단일 writer를 보장한다.
- 조회는 한 호스트로만 보낸다(VIP나 LB). 호스트 간 틱 수가 다르면 n-tick 경계가 달라질 수 있어 전환 시 스트림 클라이언트는 snapshot을 다시 받아야 한다.
- 전제: 두 호스트가 같은 순서의 스트림을 받는다(미확인).

## 6. 호스트 복구와 유실 구간 동기화

### 6.1 복구된 호스트 재시딩 (꼬리 유실)
1. X가 먼저 수신을 시작해 링에 쌓되 SQLite에는 반영하지 않는다.
2. 정상 호스트 Y의 일자 파일을 SQLite backup API로 일관된 스냅샷으로 복사한다.
3. 스냅샷 끝 K개 틱(ts, price, qty) 지문을 X의 링에서 찾아 그 다음부터 반영한다. 수신을 스냅샷보다 먼저 시작해야 겹침이 보장된다.
4. `valid_count`와 분 단위 집계를 비교해 검증한다.

### 6.2 중간 유실 탐지: 분 단위 다이제스트
- 일자 파일에 `minute_digest(minute, cnt, h)`를 추가한다. `cnt`는 invalid를 포함한 수신 틱 수, `h`는 틱별 `hash(ts, price, qty)`의 64비트 합이다. 틱 INSERT와 같은 트랜잭션에서 갱신한다.
- 합은 순서에 무관하므로 도착 순서가 조금 달라도 같은 집합이면 같은 값이다.
- 두 호스트가 지난 분(예: 2분 이전)의 `(minute, cnt, h)`를 주기적으로 교환해 비교한다. 불일치한 분이 유실 구간이다.
- 기존 `candle_1m`은 valid만 담으므로 invalid 유실을 못 본다. 그래서 따로 둔다.
- 수신부의 재접속, 링 덮어쓰기, 재시작 시각을 로그로 남기면 확인이 쉽다.

### 6.3 중간 유실 복구
- 같은 스트림에서 한쪽이 일부를 놓친 것이므로, 불일치 분에서 `cnt`가 큰 쪽이 상위 시퀀스이고 그 구간의 순서를 따르면 된다.
- `raw_seq`는 append 순서에 의존하므로 중간 삽입은 하지 않는다. **꼬리를 통째로 바꾼다.**
  1. 손상 호스트의 해당 종목 writer를 일시 정지하고 수신 틱은 링에 쌓는다.
  2. 첫 불일치 분보다 앞서고 양쪽이 일치한 분(앵커)을 잡아 앵커 이후 틱을 온전한 호스트에서 가져온다.
  3. 손상 호스트에서 앵커 이후 행을 삭제하고 가져온 틱을 순서대로 INSERT한다.
  4. `valid`는 호스트 값을 쓰지 않고 현재 `Filter`로 도착 순서대로 다시 판정한다.
  5. `valid_count`, `last_raw_seq`, `candle_1m`, `minute_digest`를 같은 트랜잭션에서 갱신한다(`rejudge`와 같은 방식).
  6. 정지 동안 쌓인 링 틱은 6.1의 지문 정렬로 이어 반영한다.
- 파일이 작으면 파일 전체 재시딩(backup API)이 더 단순하다. 큰 파일일 때만 꼬리 재작성을 쓴다.
- 복구 후 다이제스트와 `valid_count`를 다시 비교해 같을 때만 완료로 표시하고, 해당 종목의 스트림 클라이언트는 snapshot을 다시 받는다.

### 6.4 한계
- 두 호스트가 **서로 다른 곳에서** 유실했다면 어느 쪽도 상위 시퀀스가 아니므로 자동 복구가 안 된다. 병합 정렬이 모호하므로 경보 후 수동 판단으로 둔다.
- 양쪽이 동시에 놓친 틱은 복구할 수 없다.
- 지문 정렬(K개 틱)은 휴리스틱이다. 같은 내용이 K개 연속 반복되면 잘못 맞출 수 있으며 K를 크게 잡고 ts 범위로 제한하고 검증으로 잡는다. 실제 모호성은 mockfeed로 시험하지 않았다(미확인).
- 64비트 합 충돌은 사실상 무시할 수 있으나 0은 아니다.

## 7. 구현 순서 제안

1. 수신부(C)에 64비트 카운터와 `epoch`를 추가한다.
2. Go 리더를 만든다: mmap, 덮어쓰기 검증(seqlock), 커서, 갭 기록.
3. `FULL` + group commit(채널 드레인)을 적용하고 `day_stats.last_src_seq`로 멱등 재생을 구현한다.
4. 저널과 병행 기록하며 틱 수와 `valid_count`를 비교한 뒤 저널을 끈다.
5. `minute_digest`와 호스트 간 비교를 추가한다.
6. 재시딩과 꼬리 재작성을 구현하고 mockfeed로 유실을 주입해 시험한다.

## 8. 미확인 사항

- 링 헤더·슬롯 구조체 정의(C 헤더), 현재 카운터 유무
- 피크 틱률, 허용 지연, 허용 복구 시간
- 두 호스트가 같은 순서의 스트림을 받는지
- 저부하 group commit 커밋 지연 분포
- 지문 정렬의 모호성 실측
