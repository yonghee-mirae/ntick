# PRD: 체결 시세 기반 OHLC 캔들 제공 기능

2026-10-02

## 1. 개요

주식 체결 시세에서 유효 체결만으로 시간 캔들과 n-tick 캔들의 OHLCV를 산출해 차트에 제공합니다. 저장소는 SQLite입니다.

**목표**

- invalid tick을 제외한 정확한 OHLCV 제공
- 사용자 지정 (n, m)에 대해 최근 m개 n-tick 캔들을 최대 m·n건 조회로 산출
- 종목별 단일 writer와 트랜잭션으로 부분 반영 없는 커밋 보장

**범위**

| 포함 | 제외 |
| --- | --- |
| 체결 수집·저장, 수신 시 invalid 필터(교체 가능한 규칙), 과거 일자 일괄 재판정 | invalid 판정 규칙의 확정 기준 (설계 단계에서 정함) |
| 시간 캔들(1m 기반 롤업) | 호가·보조지표 계산 |
| n-tick 캔들(n, m 요청, 전일 연속) | 차트 렌더링(클라이언트) |
| 조회 API, 실시간 갱신 | |

## 2. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 유효 tick | 캔들 계산에 포함되는 체결 (`valid = 1`) |
| invalid tick | 저장은 하되 계산에서 제외되는 체결 (`valid = 0`) |
| ts | 전문의 거래소 체결 시각 (날짜 포함, ms). 수신 시각이 아님 |
| raw_seq | 일자·종목 파일 내 수신 순서. 거래소 체결번호가 없어 자체 생성 |
| T_d | 종목의 d일 유효 tick 수 |
| n | n-tick 캔들 1개를 구성하는 유효 tick 수 |
| m | 요청하는 캔들 개수. 최근부터 과거 방향 |
| r_d | d일 마지막 캔들의 tick 수. `T_d % n`, 0이면 n |
| 미완성 캔들 | tick 수가 n 미만인 일자별 마지막 캔들 |
| 일자 | 거래소 현지 시각 기준 00:00 포함 ~ 24:00 미포함 |

## 3. 기능 요구사항

모든 캔들은 유효 tick만으로 계산하며, O = 첫 체결가, H = 최고가, L = 최저가, C = 마지막 체결가, V = 체결량 합계입니다. "첫/마지막"의 기준은 시간 캔들은 `ts`(동률이면 raw_seq), n-tick은 raw_seq입니다.

### 3.1 invalid tick 처리

- FR-1. invalid tick도 원본 테이블에 저장하고 `valid` 플래그로 구분한다.
- FR-2. invalid tick은 OHLCV, tick 수, 캔들 경계 산정에서 모두 제외한다.

### 3.2 시간 캔들

- FR-3. 1분봉을 기본 단위로 집계하고, 상위 interval(3m, 5m, 1h, 1d 등)은 롤업으로 산출한다.
- FR-4. 구간은 `[시작, 종료)`이며 일자와 interval 경계는 거래소 현지 시각 기준이다.
- FR-5. 진행 중인 캔들은 미완성으로 표시한다.
- FR-5a. 유효 체결이 없는 구간의 캔들은 생략한다. 직전 종가로 채우지 않는다.

### 3.3 n-tick 캔들

- FR-6. 요청은 (n, m)으로 받고, 최근 캔들부터 과거 방향으로 m개를 반환한다.
- FR-7. 캔들 경계는 각 일자의 첫 유효 tick을 기준으로 n개씩 고정한다.
- FR-8. 일자별 마지막 캔들은 n개 미만일 수 있으며, 다음 날 tick과 합치지 않는다.
- FR-9. m이 당일 캔들 수보다 크면 전일 캔들로 이어서 채운다. 체결이 없는 날은 건너뛴다.
- FR-10. 보유 데이터가 m개에 못 미치면 존재하는 만큼만 반환한다.

### 3.4 실시간 갱신

- FR-11. 진행 중인 캔들의 갱신을 구독자에게 푸시한다.
- FR-12. n-tick은 당일 유효 tick 수가 n의 배수가 되면 다음 tick부터 새 캔들을 시작한다.

## 4. 데이터 저장 설계

저장소는 일자·종목별 SQLite 파일(`data/{YYYYMMDD}/{symbol}.db`)이며, tick은 `ts`의 현지 날짜에 해당하는 파일에 저장합니다. 일자 파일의 `day_stats.valid_count`가 T_d의 기준(source of truth)입니다.

### 4.1 테이블

| 테이블 | 위치 | 키 | 주요 컬럼 | 용도 |
| --- | --- | --- | --- | --- |
| ticks | 일자·종목 파일 | raw_seq | ts, price, qty, valid | 원본 체결, n-tick 계산 원천 |
| day_stats | 일자·종목 파일 | id (단일 행) | valid_count, last_raw_seq | T_d 카운터, 조회 상한 |
| candle_1m | 일자·종목 파일 | minute | open, high, low, close, open_ts, close_ts, volume, tick_count | 시간 캔들 기본 단위 |
| day_index | meta.db | (symbol, date) | valid_count | 장 마감 확정 T_d 기록·점검용. `day_stats`에서 재생성 가능한 캐시 |

```sql
-- data/{YYYYMMDD}/{symbol}.db
CREATE TABLE ticks (
  raw_seq INTEGER PRIMARY KEY,   -- rowid, assigned in arrival order
  ts      INTEGER NOT NULL,      -- exchange time field of the message, epoch ms
  price   INTEGER NOT NULL,      -- integer in the smallest price unit
  qty     INTEGER NOT NULL,
  valid   INTEGER NOT NULL       -- 0/1
);

CREATE INDEX ix_ticks_valid ON ticks(raw_seq) WHERE valid = 1;

CREATE TABLE day_stats (
  id           INTEGER PRIMARY KEY CHECK (id = 1),
  valid_count  INTEGER NOT NULL,
  last_raw_seq INTEGER NOT NULL
);

CREATE TABLE candle_1m (
  minute INTEGER PRIMARY KEY,          -- minute offset from 00:00 of the day (0~1439)
  open INTEGER, high INTEGER, low INTEGER, close INTEGER,
  open_ts INTEGER, close_ts INTEGER,   -- ts of the ticks behind open/close
  volume INTEGER, tick_count INTEGER
);
```

### 4.2 설계 결정

- **파일 분할**: 일자·종목 단위로 나눠 종목 간 쓰기 락이 서로 막지 않게 한다. 과거 파일은 읽기 전용이며 보관 기간은 일자 디렉터리 단위로 관리한다.
- **raw_seq**: `INTEGER PRIMARY KEY`(rowid)로 SQLite가 `max(rowid) + 1`을 부여한다. 파일당 writer가 하나이고 삭제가 없으므로 수신 순서와 일치하며 별도 카운터나 복구가 필요 없다. `AUTOINCREMENT`는 불필요하다.
- **raw_seq의 역할**: 개수가 아니라 순서 키다. n-tick 정렬, 스냅샷 상한(`raw_seq <= last_raw_seq`), 정정 대상 행 식별, 시간 캔들의 ts 동률 판정에 쓴다. invalid로 인한 번호 건너뜀은 문제가 되지 않는다. 순서는 소스가 전달한 순서이므로 실제 체결 순서와의 일치는 소스의 순서 보장에 의존한다 (8장).
- **정렬 기준**: n-tick은 raw_seq, 시간 캔들은 `ts`(동률이면 raw_seq)다. 이 때문에 같은 tick 집합에서도 두 캔들의 O/C가 다를 수 있다.
- **같은 파일**: `day_stats`와 `candle_1m`은 `ticks`와 같은 파일에 둔다. WAL 모드에서는 ATTACH한 파일 간 트랜잭션이 원자적이지 않기 때문이다.
- **valid_seq 미사용**: 사후 invalid 정정 시 재번호 부여를 피한다.
- **day_index**: 장 마감 시 확정 T_d를 기록하고 점검에 쓴다. 조회의 T_d는 스냅샷 일관성을 위해 항상 일자 파일의 `day_stats`에서 읽으며, 조회 최적화에 쓰는 것은 실측 후 판단한다. 다른 파일이므로 일자 파일과 원자적이지 않다 (6.3).
- **파일 수**: '일자 × 종목'이며 WAL에서는 파일당 `-wal`, `-shm`이 추가된다. 연결은 LRU 풀로 관리하고 파일 디스크립터 한도를 점검한다. 장 마감 후 과거 파일은 체크포인트 후 rollback journal 모드로 전환할 수 있다.

### 4.3 SQLite 요구 버전

- UPSERT 3.24 이상, 윈도 함수 3.25 이상.

## 5. 요청 처리 설계

### 5.1 API

```
GET /candles?symbol=005930&type=time&interval=5m&from=...&to=...
GET /candles?symbol=005930&type=tick&n=100&m=200
WS  /candles/stream?symbol=005930&type=tick&n=100
```

### 5.2 n-tick 조회 알고리즘

일자별 T_d로 필요한 tick 수를 계산해 일자당 최근 L_d건만 역순 조회합니다. 전체 조회량은 최대 m·n건입니다.

1. 종목 파일이 있는 일자를 최신부터 과거 방향으로 순회하며 각 파일의 `day_stats`에서 T_d를 읽고, T_d > 0인 일자만 쓴다.
2. 각 일자에서 `c_d = ceil(T_d / n)`, `take = min(remaining, c_d)`, `r_d = T_d % n` (0이면 n), `L_d = r_d + (take − 1)·n`을 계산한다.
3. 해당 일자 파일에서 최근 L_d건을 조회한다.
4. 조회 결과(최신순)의 첫 r_d건을 마지막 캔들로, 이후 n건씩 잘라 캔들을 만든다. 캔들 내부는 시간순으로 뒤집어 O/C를 정한다.
5. `remaining -= take`. 0이거나 최대 조회 일수에 도달하면 종료한다.

```sql
-- data/{YYYYMMDD}/{symbol}.db
SELECT price, qty FROM ticks
WHERE valid = 1 AND raw_seq <= :last_raw_seq
ORDER BY raw_seq DESC
LIMIT :L_d;
```

### 5.3 시간 캔들 조회

`candle_1m`을 범위 조회한 뒤 interval 단위로 롤업한다.

### 5.4 캐시

| 대상 | 키 | 무효화 |
| --- | --- | --- |
| 과거 일자 n-tick 캔들 | (symbol, date, n) | 해당 일자 재판정 시에만 |
| 당일 완성 n-tick 캔들 | (symbol, date, n, k) | 없음 (당일은 재판정하지 않음) |
| 최근 유효 tick | 종목별 링버퍼(K개) | 항상 최신 유지 |

- `L_d ≤ K`인 당일 요청은 DB를 거치지 않는다.
- 자주 쓰는 n은 장 마감 후 배치로 미리 생성할 수 있다.

### 5.5 실시간 갱신

- writer가 커밋 후 `(T, last_raw_seq)`와 신규 유효 tick을 이벤트로 발행한다.
- 구독 서버는 진행 중인 캔들을 갱신해 푸시하고, `T % n == 0`이 되면 캔들을 완성 처리한다.
- WS 메시지는 JSON이며 `candle` 필드는 REST와 같다(snake_case, 가격·수량 정수, 시각 epoch ms). 연결 직후 `{"type":"snapshot","candle":{진행 중 캔들}}`, 커밋마다 `{"type":"update","candle":{...}}`, 완성 시 `{"type":"complete","candle":{...}}`를 보낸다(tick은 `T % n == 0`, time은 다음 버킷 시작).
- 시간 캔들에서 늦게 도착한 tick이 이미 푸시한 과거 분봉을 바꾸면 `{"type":"invalidate","start":ms}`를 보내고, 클라이언트는 해당 구간을 재조회한다.

## 6. 정합성과 장애 대응

체결 insert, `day_stats` 카운터, `candle_1m` 갱신을 하나의 트랜잭션으로 커밋해, 세 값이 함께 반영되거나 함께 롤백되도록 합니다.

### 6.1 단일 writer

- 종목마다 writer를 하나씩 두어 종목 간 쓰기를 병렬로 처리한다. 종목은 해시로 worker 스레드에 고정 배정하며, 한 종목 파일에는 항상 한 worker만 쓴다.
- worker는 종목별로 micro-batch(수십 ms 또는 수백 건)로 묶어 커밋하고, 소스에서 받은 순서 그대로 insert한다.

```sql
BEGIN IMMEDIATE;
INSERT INTO ticks (ts, price, qty, valid) VALUES (...), ...;  -- raw_seq auto-assigned
INSERT INTO day_stats (id, valid_count, last_raw_seq)
VALUES (1, :valid_in_batch, last_insert_rowid())
ON CONFLICT (id) DO UPDATE
SET valid_count  = valid_count + excluded.valid_count,
    last_raw_seq = excluded.last_raw_seq;
-- candle_1m upsert: replace open/open_ts if (ts, raw_seq) is earlier than the stored one,
-- close/close_ts if later; high/low/volume/tick_count accumulate
COMMIT;
```

### 6.2 스냅샷 읽기

- T_d 조회와 체결 조회 사이에 새 체결이 들어오면 경계가 어긋난다. 둘을 하나의 읽기 트랜잭션(WAL 스냅샷)으로 묶고 `raw_seq <= last_raw_seq` 상한도 건다.
- 읽기 트랜잭션은 짧게 유지한다. 오래 열려 있으면 WAL 체크포인트가 막힌다.

### 6.3 과거 일자 일괄 재판정

- 재판정은 최소 하루가 지난 일자만 대상으로 하며, 당일 데이터는 재판정하지 않는다. 따라서 tick 단위 사후 정정과 당일 구독자 대상 정정 푸시는 없다.
- 일자 파일에서 `valid`를 다시 판정하고, 같은 트랜잭션에서 `valid_count`와 `candle_1m`을 재계산한다. 과거 파일은 읽기 전용이므로(4.2) 재판정 절차(쓰기 전환 방식)는 설계 단계에서 정한다.
- 일자 파일 커밋 후 `day_index`를 `day_stats.valid_count` 절대값으로 덮어쓴다. 별도 파일이라 원자적이지 않으나, 일자 파일이 기준이므로 실패해도 재시작·장 마감 점검 때 재동기화하면 된다.
- 해당 일자의 n-tick 캐시를 무효화한다 (5.4).

### 6.4 복구와 점검

- 커밋되지 않은 배치는 전부 롤백되므로 롤백 복구 로직은 필요 없다. raw_seq도 다음 insert에서 `max(rowid) + 1`로 이어진다.
- 재시작·소스 재연결 시 체결 누락·중복 처리는 소스의 재전송 지원 여부에 따라 정한다. 거래소 체결번호가 없어 같은 시각·가격·수량의 체결이 중복인지 별건인지 구분할 수 없다 (8장).
- 장 마감 시 `COUNT(valid=1)`과 `valid_count`를 비교해 드리프트를 탐지하고, 확정 T_d를 `day_index`에 기록한다. 이때 `day_index`와 `day_stats`의 불일치도 재동기화한다.

## 7. 비기능 요구사항

| 항목 | 요구사항 | 목표치 |
| --- | --- | --- |
| 수집 처리량 | 초당 최대 체결 수를 종목별 writer로 처리 | 미정 |
| n-tick 조회 지연 | 조회량 ≤ m·n, 캐시 적중 시 DB 미접근 | 미정 |
| 요청 상한 | m·n 최대값, 최대 조회 일수 | m ≤ 1,000, n ≤ 10,000, 최대 조회 30일 |
| 실시간 지연 | 커밋 후 구독자 푸시까지 | 미정 |
| 내구성 | 프로세스 장애 시 커밋분 유실 없음 | `synchronous=NORMAL`로 시작 |
| 보관 기간 | 일자 디렉터리 단위 삭제 | 미정 |

**SQLite 운영 설정**

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;  -- use FULL if durability across power loss is required
PRAGMA busy_timeout = 5000;
```

- `NORMAL`은 정전·OS 장애 시 마지막 몇 트랜잭션이 유실될 수 있으나, 체결과 카운터가 함께 사라져 정합성은 유지된다.
- DB 파일은 로컬 디스크에 둔다. 네트워크 파일시스템에서는 WAL을 쓸 수 없다.

## 8. 미결 사항 및 가정

**확정된 가정**

- n-tick 경계는 일자별 첫 유효 tick 기준이며, 마지막 캔들은 부족할 수 있다.
- m이 당일 캔들 수를 넘으면 전일로 이어지고, 일자 간 부족 캔들은 합치지 않는다.
- 저장 파일은 일자·종목 단위로 분할하며, 일자는 `ts`의 거래소 현지 날짜로 정한다.
- `ts`는 전문의 거래소 체결 시각(날짜 포함, ms)이다. 데이터 소스는 체결번호를 제공하지 않으며 raw_seq는 수신 순서로 자체 생성한다.
- 정렬 기준은 n-tick은 raw_seq, 시간 캔들은 `ts`(동률 시 raw_seq)다.
- 체결이 없는 시간 구간의 캔들은 생략한다.
- `ts`는 epoch ms로 저장한다. 일자와 `minute`은 종목별 거래소 타임존(설정)으로 계산하며, `minute = (ts − 현지 00:00의 epoch ms) / 60000`이다.
- invalid는 수신 시 교체 가능한 규칙 기반 필터로 판정한다. 별도 판정 시스템·채널은 없다. 이후 변경은 최소 하루가 지난 일자의 일괄 재판정으로만 한다.
- 거래소 타임존은 Asia/Seoul이다. 종목 수는 사전에 정하지 않고 수신 전문의 종목코드로 동적으로 처리한다.
- 장 마감 시각은 20:00(Asia/Seoul, 설정값)이며, 이 시각에 당일 T_d를 `day_index`에 확정한다.
- 재연결 시 소스는 재전송하지 않으며 끊긴 구간의 누락만 허용한다. 중복 제거는 하지 않는다.
- 자정 전후에 충분한 break time이 있어 자정 경계를 넘는 늦은 tick은 고려하지 않는다.
